    Home lab architecture

    This section describes the architecture of the home lab: one design specification per subsystem, whose status table tells design from reality, the reference pages beside them, and the todo list for the whole lab.

    Specifications Directory Index

    Specification Description Current Implementation Status
    Home Lab Bootstrapping Global VM installation infrastructure: Nix-native custom installer ISO, secure bootstrap key loading with Git-tracking guardrails, and nixos-anywhere. Fully Implemented
    NixOS VMs on Proxmox Reusable framework for NixOS VMs: the proxmox-vm role, host structure with Disko layouts, and the Terraform VM provisioning pattern. Fully Implemented
    Declarative Integration Testing Design of the NixOS test generator framework (make-test.nix), dynamic test discovery, and parallel GHA matrix CI pipeline. Fully Implemented
    NixOS LXC Containers on Proxmox Reusable framework for NixOS LXC containers: the proxmox-lxc role, system.build.tarball templates, and the Terraform provisioning pattern. Fully Implemented
    NAS LXC Container NixOS LXC containers on each Proxmox node exposing host ZFS datasets as SMB shares via bind mounts, plus the Syncthing service. Builds on the proxmox-lxc framework. Partially Implemented
    Monitoring Alerting Prometheus Alertmanager in the monitoring backend stack: Telegram notification routing, the severity model, the alert rules catalogue, and the highly available backend pair. Fully Implemented
    Network Boot Service Boot server on hl02 that network-boots any lab host on demand through a per-host toggle: the Raspberry Pi path (proxy DHCP and TFTP) now, x86 PXE deferred, the vendor image over NFS as the first payload, and Raspberry Pi re-provisioning as the first consumer. Partially Implemented
    Backups Restic backups of the workload state on the Debian hosts: one repository per host on the NAS share, the declared-coverage model, and the verification ladder from structural checks to the monthly restore drill. Partially Implemented
    MQTT Broker The Mosquitto broker for the smart home workloads as a NixOS module on hl02: the mosquitto role, its integration test check, the TCP probe, and the cutover from the raspberrypi2 Compose stack. Fully Implemented

    Specifications to write and TODOs

    This section is the centralized list of future work and todo items for the whole home lab; specifications carry no future work sections of their own. Items are grouped by theme, and stay here until they are implemented and reflected in the relevant specification, or explicitly discarded. The software considered for each need, in use or candidate, is tracked in Software candidates: only active evaluations become items here. An item is work with a next step: a decision that has been taken leaves the list once the owning specification records it, and an undated idea with no first step waits in the Ideas subsection until it gets one.

    Bootstrapping and provisioning

    • Power on hosts through their BMC from ferrarimarco_home_lab_boot_bare_metal (2026-10-28): the role only sends Wake-on-LAN packets to every MAC in network_interfaces and waits for SSH. First verify that path: the packets are sent from inside the Ansible container, delegated to localhost, and the runner does not use host networking, so the broadcast may never leave Docker's bridge (a packet sent from raspberrypi2 did wake pve2 on 2026-10-06, so the host side works: the i210 reports Wake-on: g). Test the playbook against pve2 while it is off, watching the plug; if it fails, run that playbook with host networking or delegate the send to a LAN host. Then, for hosts that declare a BMC address (pve2 does, reserved on the gateway as pve2-bmc), use community.general.ipmi_power before the SSH wait, delegated to the control machine, with the credentials from the vault; it needs the pyghmi library in the Ansible container image.
    • Manual steps left in the provisioning of a new host: copy the ESPHome secrets; configure the Ansible Vault password file and the per-host vault files; configure the SSH keys; join the host to the tailnet (tailscale up is interactive, one run per node; the NAS spec records the deferral and the candidates); configure unattended updates for the Nix hosts (the Debian hosts and the Proxmox nodes are covered for the Debian origins by the node role's unattended-upgrades stack; the Proxmox origin stays manual, see the item on automating the Proxmox updates under Host configuration); run Ansible; run Terraform (networking; the storage stack is applied on both nodes).
    • Network boot service follow-ups, per the Network Boot Service spec:
      • A second server instance on pve2, so that pve1 and hl02 are covered too. It must be a standby that answers only while the hl02 instance is down, or share its toggle state: the bootloader takes the first "Raspberry Pi Boot" reply and gives up when that server has no directory for the host. Depends on: the x86 PXE path (deferred, see the spec) and the pve2 power reduction (Host configuration).
      • Declared rescues beside the toggle command (deferred on 2026-11-05 until the dry rescue of 2026-11-07 had exercised the command path): a rescue flag per host in the netboot-server role that starts the toggle at boot and at activation; a reconcile step acting only on the hosts whose declaration changed since the previous activation, so a rescue started by command survives unrelated deployments; a boot-time purge limited to the undeclared hosts; a start that keeps an existing export. Then decide whether the command path stays (hybrid) or the flag becomes the only way to start and stop a rescue (two deployments per rescue, none while the deployment path itself is broken).
      • Documentation: the provisioning guide (EEPROM editing from the OS, the rescue procedure, the manual follow-ups), the restore recipe (Backup), and the unresponsive host runbook.

    Issues to solve

    • Recurring cam-3 ffmpeg VAAPI decode crashes on hl01 (about 11 per hour: Failed to sync surface then hwdownload failures; they persist over RTSP TCP, so stream transport corruption is ruled out). Hardware acceleration stays enabled by decision (2026-09-23): the Frigate watchdog recovers capture each time and the Frigate alert rules watch for lasting degradation. Angles: Intel media driver and kernel versions, the camera sub-stream H.264 parameters, Frigate and ffmpeg updates.
    • Frigate doesn't restart because the cam3 name is not yet available. Restart it manually from the Frigate UI.
    • Home Assistant doesn't connect to Zigbee2MQTT and Telegram (DNS error): /etc/resolv.conf is empty. Need to wait for the host network to be ready?
    • Budget the hl01 root disk: Frigate's storage maintainer frees recordings only when the free space drops below one hour of camera bandwidth (about 1.8 GB), so the free space oscillates around that floor, which on a 38 GB disk matched the 5 percent NodeFilesystemSpaceCritical threshold and made the alert flap (2026-10-04, fixed by growing the disk to 64 GB). Size the disk for retention days times daily recording volume (about 1 GB per day) plus the Prometheus TSDB growth under its 60-day retention, and resize before the headroom shrinks to that floor.
    • raspberrypi2 stability follow-ups (the stability notes record the episodes):
      • Optionally prove the hardware watchdog recovery path end-to-end with a deliberate kernel crash (echo c > /proc/sysrq-trigger): the host should self-reboot within the 15 second timeout. Schedule it consciously, since it has the usual unclean-shutdown cost.
      • Prune the unreferenced vault_raspberrypi2_monitoring_nut_* variables from the raspberrypi2 Ansible vault (NUT moved to pve1; the host_vars references were removed on 2026-09-14).
    • ONT hang and power cycle (2026-11-04): the ZTE ONT hangs in a state that only a power cycle clears, as the ONT notes record; its admin interface has no reboot control and the device keeps no log, so a smart plug is the only remote recovery lever and the router log the only record of an outage start (Networking has the log retention item). Design to assess: a Zigbee plug on the ONT (whether it sits on one of the studio plugs today is not recorded), switched over a path that does not need the WAN (Zigbee2MQTT on raspberrypi2 and the MQTT broker on hl02, from a Home Assistant automation or from the WAN check unit) when the check has failed for several consecutive runs with the gateway's Ethernet link up and no PPPoE reply, at most one cycle per hour. Failure modes to weigh: a cycle during an ISP outage is wasted but harmless; the plug, Zigbee2MQTT, and the check all depend on raspberrypi2; an ONT reboot drops the WAN for about a minute, so the trigger must not fire on a short blip (the check's fails=1 setting is the current sensitivity). Depends on: the WAN check telling an ONT hang from an ISP outage (Networking).

    Reliability and resilience

    • raspberrypi2 root filesystem stall watchdog (postponed 2026-10-13): the armed hardware watchdog only resets a hung kernel, while the host's failure is a root I/O stall that PID 1 survives. The design reviewed on 2026-10-12 is recorded in the stability notes, so the next attempt starts from it. Postponed because a rehearsal only proves that the unit reboots the host when its own probe hangs; whether the probe sees the real failure needs a way to trigger the stall deliberately (a controlled reset or power cut of the USB bridge), and a watchdog that can reboot the alerting backend's host for the wrong reason is worse than none. Depends on: a reproducible trigger for the stall, to be designed with the UAS quirk (Host configuration). Until then a stall means a power cycle.

    Security

    • Pin every GitHub Action to a commit SHA: 4 of the 14 third-party actions the workflows use are SHA-pinned, the rest by tag, and config/lint/zizmor.yaml ignores the unpinned-uses audit for twelve workflows until they are. Pin them with the release tag in a trailing comment and drop the ignores.
    • Restrict the Frigate configuration file to root only (the node role renders it with mode 0640 today).
    • Mosquitto encryption, authentication, and mTLS: the broker runs on hl02 as a NixOS module (MQTT Broker) that takes password files and certificates from paths on the host, so this needs a secret delivery path for the NixOS hosts, which none has yet (the open listener needs none).
    • NixOS hardening, in order of intrusiveness: enable the NixOS firewall with the Tailscale interface trusted; harden each service unit with the systemd sandboxing directives (ProtectSystem, ProtectHome, NoNewPrivileges, the ProtectKernel family), using systemd-analyze security as the yardstick; audit every execve with the kernel audit subsystem and ship the logs off the host; strip the default packages. Later options: an ephemeral root with opt-in persistence (impermanence or preservation), and noexec on every mount except the Nix store, which can break Nix builds and needs a break-glass path back.

    Host configuration

    • Automate the Proxmox package upgrades, with a human in the loop (decided to design on 2026-11-10): the vendor prescribes apt full-upgrade and warns that apt upgrade can leave a partially upgraded state; unattended-upgrades has the latter's semantics by design (it holds back any step that removes a package), so the node role runs it for the Debian origins only and the Proxmox origin (pve-manager, the kernel, ZFS) stays manual, nudged by AptUpgradesPending (191 packages had accumulated on pve1 by 2026-11-10, 34 of them security fixes). Candidate shapes: a host timer that refreshes and downloads, then notifies and waits for a human go before the upgrade and the reboot; or a scheduled run of the OS packages playbook from a host that is always on (the control machine suspends). Any shape needs a reboot window, the guest start ordering on pve1 (hl01, hl02, the NAS container, whose rpool-usb-2 pool had no import unit until the reboot of 2026-11-10 exposed it), the proxmox-ve apt hook as the only built-in guard against a removal, and an alert for a run that failed or never happened. The cost side of the rejected automatic variant: unattended removals and hypervisor changes nobody reviews, which the staff position in the Proxmox forum thread advises against.
    • Converge pve2's root filesystem and bootloader with pve1's (2026-10-22): pve1 boots a ZFS root through proxmox-boot-tool with systemd-boot, which keeps every ESP in sync and takes the kernel command line from /etc/kernel/cmdline; pve2 was installed on LVM with an ext4 root and boots through GRUB, so its root has no checksums, compression, or snapshots to roll back an upgrade. The Proxmox role's kernel task reads the boot layout and writes the GRUB variant since 2026-11-10, not yet run on pve2 (the pve2 first full node run item under CI/CD). Align at pve2's next reinstall by choosing a ZFS root in the installer with Secure Boot off (Proxmox falls back to GRUB with it on); a reinstall only for this is not worth its cost (guests re-created by Terraform, the data pools exported and imported, the NAS container's state directories on the root disk carried across).
    • pve2 power reduction before running it 24/7: the goal is to run pve2 around the clock, but it stays powered off until its idle draw (about 45 W at the wall) comes down. The measurements, the levers with their status, the experiment log, the BIOS export, and the decisions taken are in the host power guide. Remaining steps:
      • Keep watching the SATA link power management the BIOS change of 2026-10-06 enabled: before declaring the host fit for 24/7 duty, check the kernel log for ata1-ata3 resets and the UDMA_CRC_Error_Count attributes after a few days of uptime, and run a ZFS scrub once the pools hold enough data to exercise the links (about 1 GB today).
      • Replace the PSU, last, so it is measured at the final DC load.
      • Deferred until the pve2 workload is defined: the CPU governor, the energy performance bias, and the memory frequency, all of which trade performance for power under load; compare them with a controlled load on the plug, then decide what goes into the BIOS file or the host configuration.
      • The power instrument depends on raspberrypi2 (the Zigbee plugs reach Home Assistant through Zigbee2MQTT there); the network coordinator (Smart home) removes that dependency.
      • Depends on: a stable BMC address for remote recovery during runtime experiments (Networking). Blocks: the media second copy on tank-hdd (Backup); the Proxmox node downtime alerts stay enabled by choice until pve2 runs 24/7 (Monitoring and alerting).
    • Prometheus node exporter on the Asus RT-AX86U: copy the node public key to the router, trust its host key on the connecting node, run the arm64 release binary from USB storage, relaunch it when not running from a cru cron entry, add the router to the node scrape job, and verify the netdev collector reports the interface counters, since some exporter releases failed on this firmware (reference). The stock firmware has no init-start hook and its script_usbmount variable is blocked on recent builds (checked 2026-10-23; the gateway notes have the evidence), so the known launcher is the one jacklul/asuswrt-scripts uses: a USB stick carrying a fake Download Master package whose init script starts the scripts after the mount. No USB storage is attached to the router today, so this item starts with that stick.
    • raspberrypi2:
      • Enable TRIM on the external SSD (reference).
      • Force the Argon One M.2 bridge (ASMedia 174c:1156, the root SSD) off the uas driver with usb-storage.quirks: 174c:1156:u in the host's raspberry_pi_kernel_command_line_options (the node role rewrites cmdline.txt and reboots since 2026-11-09).
